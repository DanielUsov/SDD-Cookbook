Эталон: `OpenSpec/cases/Sber/` (пример реализации) и общие документы `OpenSpec/store/`, `OpenSpec/gates/`, `OpenSpec/roles/`. При расхождении правильным считается то, что описано в кейсе Sber (так решил пользователь 2026-10-06).

## Суть

- **Чёрный ящик.** Аналитик описывает взаимодействие (контракты, модель данных в общем виде, интерфейс, интеграции), но не реализацию. Реализацию решают разработчики.
- **Две спецификации.** Store (общий репозиторий в Bitbucket) хранит подробные ФТ. Кодовый репозиторий хранит свой master spec (реализация и поведение своей части).
- Работа аналитика идёт через агента (Gigacode) в формате brainstorm. Контекст берёт **только из Store**: master spec, архив, БТ. Доступа к коду нет.

## Структура Store

`docs/`, `business-requirements/` (BRD из Confluence), `changes/<JIRA-ID>-<суффикс>/`, `changes/archive/`, `specs/<модуль>/`.

Фича: `FRD.md` (таблица в начале: Jira, название, тип, БТ, модули, части, impact; идея и механизм), `BFRD.md`, `FFRD.md` (интерфейс внутри него), `contracts/` (`api.yaml` как фрагмент OpenAPI с `x-removed`, `data-model.yml` как логическая дельта без привязки к СУБД, `integrations.*`). Нет области, нет файла. Жёсткий шаблон ФТ отложен.

## Теги и версии

- Тег фичи `PROJ-1234/vN` ставит CI автоматически при мерже PR в master (ID из имени ветки `feature/`/`fix/`).
- Тег релиза Store `x.y.z` (SemVer) ставит аналитик вручную после архивации на feature freeze (ветка `release/x.y.z`). Версия по максимальному `impact` (major, minor, patch).
- Версии Store и приложений **независимы**. Сборка фиксирует, на какой версии Store основана.
- Submodule `openspec/store` пинится **только на тег** (тег фичи в работе, тег релиза после архивации). Не на коммит и не на ветку.

## Архивация

На feature freeze, а не при мерже кода. Скрипт `store-archive` (обёртка над `openspec archive --skip-specs`, штатная архивация не вливает yaml и контракты) вливает файлы в `specs/<модуль>/`. Фича архивируется, когда все задачи BE и FE в релизе закрыты, иначе остаётся в `changes/`.

## Кодовые репозитории

Локальная схема: форк superpowers-bridge (`openspec/schemas/`). Метаданные change в `proposal.md`: `jira-id` (всегда), `store-feature` и `store-version` (если есть фича в Store). Ссылка по ID фичи и версии, не по пути. Папки changes без Jira ID. Ветки gitflow `feature/PROJ-1234`. Несколько changes одной задачи, одна ветка. Локальный change архивируется до мержа PR в той же ветке. Матрица чтения Store лежит в `docs/` Store, это поведение по умолчанию.

## Проверки

В репозитории в ходе работы (отчёт `verify`, pre-push хук: блокирует ошибки формата, остальное предупреждает). В сборке Bitbucket (Jenkins) только codegen по API (код генерируется при сборке, не коммитится). Моделей данных, поведения, интерфейса, интеграций формально не проверяем.

## Граничные случаи

Изменение ФТ в разработке (новый тег, комментарий в Jira вручную, diff между тегами), исправление ФТ (`fix/`, impact patch, тот же процесс), разделение фичи на независимые фичи в Store, change без фичи в Store (обязателен `jira-id`).

## Что не решено

Жёсткий шаблон FRD; формат текстовых дельт для store-archive; размещение корня OpenSpec в корне репозитория Store; пост-проверка тега релиза в Jenkins; имя ветки `release/x.y.z`.
