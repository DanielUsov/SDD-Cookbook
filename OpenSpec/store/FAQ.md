# Как после этапа 2, будет происходить этап 3? 
Переход от локальной разработки (Этап 2) к верификации (Этап 3) инициируется инженером и передается в контур автоматизации:
1. **Завершение чек-листа:** разработчик и AI-агент доводят реализацию до конца, закрывая все пункты в локальном файле `tasks.md` (`[x]`).
2. **Создание Pull Request:** разработчик пушит feature-ветку и открывает PR в репозитории конкретного сервиса (Backend или Frontend).
3. **Триггер пайплайна:** событие открытия или обновления PR автоматически запускает сборочные и проверочные джобы CI/CD. С этого момента управление процессом переходит к автоматическим гейтам, которые блокируют слияние при любых расхождениях с мастер-спецификацией.
# Как это будет проверятся?
Проверка в CI/CD строится по принципу многоуровневого детерминированного барьера, исключающего субъективную оценку:
- **Аудит фиксации тега (Tag Pinning Gate):** раннер проверяет, что подмодуль или ссылка на Store зафиксированы строго на конкретном SemVer-теге (например, `v1.5.0`), а не на плавающей ветке `main` или случайном коммите.
- **Валидация выполнения скоупа:** команда `openspec validate --archived` гарантирует, что в локальном `tasks.md` не осталось незакрытых задач.
# Как будет проверятся объем инкремента мастер спеки с кодом и полнота мастер спеки?
Чтобы подтвердить, что изменения в кодовых сервисах точно и в полном объеме покрывают задумку аналитика (без самодеятельности и пропусков), применяются следующие барьеры:
**Дельта-формат как жесткая граница инкремента:**
- В OpenSpec объем изменений строго фиксируется маркерами `## ADDED Requirements`, `## MODIFIED Requirements` и `## REMOVED Requirements`.
- Сервисы обязаны реализовывать только то, что задекларировано в дельте спецификации.
**Контроль выполнения скоупа задач (`openspec validate --archived`):**
- На уровне сервиса разработчик декомпозирует требования в локальный чек-лист `tasks.md`.
- Перед слиянием и архивацией CLI проверяет закрытие всех задач: если хотя бы один чекбокс `[ ]` остался неотмеченным, команда `openspec validate --archived` завершается с ошибкой и блокирует CI.
2. **Контроль дрифта кодогенерации (Codegen Drift Gate):**
- Сгенерированные типы, DTO и Zod-валидаторы строятся напрямую из схем Store (`npm run codegen`).
- Если разработчик попытался вручную изменить контрактные интерфейсы в коде или забыл обновить сгенерированные файлы под версию схемы, сборка немедленно падает.
# Как репо с мастер спекой будет подключен у людей?
Подход через Git Submodules. Store внутрь кодового репозитория как Git Submodule (например, в путь `.openspec/store`), физически находится в отдельной папке внутри кодового репозитория, зафиксирован на конкретном коммите, и разработчик регистрирует его в CLI по относительному пути (`openspec store register ./.openspec/store --id team-plans`).

# Когда при написании спеки, мы заставляем модель сверятся с кодом несмотря на наличие мастер спеки?
Пред началом работы от команд backend и frontend потребуются общая схема DB и Swagger(OpenAPI). Любое кастомное поведение может быть настроено через custom OpenSpec schemas. Непосредственно сам "просмотр" может быть организован на машине аналитика 3 способами.
#### Вариант 1. Мультирепозиторный режим OpenSpec Workset (Основной подход)
OpenSpec поддерживает объединение несвязанных репозиториев в единую сессию редактора:
Аналитик в терминале выполняет команду:
```bash
openspec workset create feature-analysis 
\ --member ~/openspec/team-plans 
\ --member ~/src/backend-service 
\ --member ~/src/frontend-web 
\ --tool code
```
#### Вариант 2. Детерминированный сбор контекста (CLI-харвестер)
Если кодовые базы огромные и полное открытие проектов перегружает контекст модели (риск _context drift_ и галлюцинаций), процесс «просмотра» сужается до атомарных выжимок перед запуском агента:

- **Frontend As-Is:** утилита `repomix` упаковывает только целевую форму и её хуки (`npx repomix --include "src/features/auth/OtpForm.tsx" --output context/fe-asis.xml`).

- **Backend As-Is:** `repomix` упаковывает только контроллер, DTO и миграцию (`npx repomix --include "src/main/**/AuthController.java,src/main/**/dto/**" --output context/be-asis.xml`).

- **API:** утилита `openapi-format` вырезает из Swagger только целевой эндпоинт в `api-slice.json`
#### Вариант 3. Подключение через MCP (Model Context Protocol)
Подразумевается простое написание простого mcp для доступа к репозиториям, возможно использование уже готовых для доступа к Bitbucket.

- В агентное окружение аналитика подключаются MCP-серверы чтения кода (например, ripgrep/ast-grep MCP).

- Агент не читает репозиторий «ковровым» методом, а точечно вызывает инструменты поиска по ключевым словам (имена эндпоинтов, аннотации Spring, интерфейсы TypeScript).
