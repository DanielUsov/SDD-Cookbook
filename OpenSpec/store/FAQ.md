# Как после реализации в кодовом репозитории происходит проверка?
Переход от локальной разработки к проверке инициируется инженером:
1. **Завершение задач:** разработчик и AI-агент доводят реализацию до конца, закрывая все пункты в локальном файле `tasks.md` (`[x]`).
2. **Отчёт о проверках:** в артефакте `verify` фиксируются результаты проверок (см. ниже), он прикладывается к PR.
3. **Архивация change:** разработчик архивирует change в локальный master spec в той же ветке, до мержа PR.
4. **Pull Request:** разработчик пушит ветку (`feature/PROJ-1234`) и открывает PR в репозитории своего сервиса. Перед пушем срабатывает pre-push хук.
5. **Сборка:** открытие или обновление PR запускает сборку, которая проверяет соответствие кода API-контракту из Store (codegen).

# Как это будет проверяться?
Проверки разделены по месту и строгости, потому что механически проверяется только контракт взаимодействия. Остальное это ответственность разработчиков (концепция чёрного ящика).
- **Pre-push хук (в репозитории).** Блокирует push при ошибках формата: имя ветки не соответствует `feature/PROJ-1234`, нет `jira-id` в change, submodule Store не пинован на существующий тег или не совпадает с `store-version`. Предупреждает (не блокирует) об отсутствии `verify` у завершённого change и о неархивированном завершённом change.
- **Отчёт `verify` (в репозитории).** Результат проверок, который читает ревьюер. Включает сравнение опубликованного контракта сервиса с контрактом Store.
- **Сборка (Jenkins).** Единственная автоматическая проверка соответствия в сборке: codegen. Полный контракт строится из `specs/` Store на пинованном теге плюс фрагменты `api.yaml` фич из changes этого PR, код генерируется при каждой сборке и **не коммитится**. Рукописный код, не соответствующий сгенерированным интерфейсам и типам, ломает сборку.

Подробнее: [[OpenSpec/gates/Контроль соответствия]].

# Как будет проверяться объём реализации относительно ФТ?
Жёстко проверяется только контракт взаимодействия (codegen), поэтому реализация не может «разойтись» с `api.yaml`: интерфейсы и типы генерируются из Store.
- **Дельта как граница.** Фича в Store описывает изменение (фрагмент контракта, дельту модели данных). Локальные specs change используют дельта-формат OpenSpec (`## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements`).
- **Скоуп change.** В `tasks.md` разработчик декомпозирует работу. Закрытие задач проверяет pre-push хук (предупреждение) и отчёт `verify`.
- **Всё остальное** (модель данных, поведение, интерфейс, интеграции) проверяет разработчик и ревью. Формальных проверок нет: это чёрный ящик.

# Как репозиторий Store будет подключен у людей?
Подход через git submodule. Store подключается внутрь кодового репозитория (путь `openspec/store`), физически лежит в проекте и **пинится на тег**: тег фичи `PROJ-1234/vN` во время работы, тег релиза Store `x.y.z` после архивации. Ни на коммит, ни на плавающую ветку `master` пинить нельзя. Если нужно, Store регистрируется в CLI по относительному пути (`openspec store register ./openspec/store --id <id>`).

Подробнее: [[Подключение Store к кодовым репозиториям]], [[Версионирование и теги Store]].

# Сверяется ли агент аналитика с кодом, несмотря на наличие master spec?
Нет. Агент аналитика берёт текущее состояние системы **только из Store**: master spec по модулям, архив прошлых фич и БТ. Доступа к коду и к master spec кодовых репозиториев у него нет, иначе в контекст попали бы детали реализации, а это нарушает принцип чёрного ящика.

- **Перед началом работы** (внедрение) в Store импортируются существующие контракты (Swagger/OpenAPI) и логическая модель данных, а также существующие ФТ из внешней базы знаний. С этого момента они становятся основой для агента.
- **Если Store и реальность разошлись**, это оформляется как исправление ФТ: аналитик и разработчик вместе решают в задаче трекера, где ошибка. См. [[OpenSpec/gates/Исправление ошибки в ФТ]].
- **Агент разработчика** может читать больше: по умолчанию он следует матрице чтения, но разработчик вправе прямым промптом расширить чтение.
