# FRD: фильтры в списке заявок

| Поле | Значение |
|---|---|
| Jira | HRPPRBCI-XXXX |
| Название | Фильтры в списке заявок |
| Тип | feature |
| БТ | [BRD-request-filters.md](../../business-requirements/BRD-request-filters.md) |
| Модули | requests |
| Части | backend, frontend |
| Impact | minor |

## Идея

Оператор сужает список заявок по статусу, периоду создания и исполнителю, чтобы быстро находить нужную заявку (цель БТ: не более трёх действий).

## Основной механизм

1. На экране списка заявок над таблицей появляется панель фильтров.
2. Выбранные фильтры уходят в запрос списка заявок как параметры.
3. Backend возвращает только заявки, подходящие под **все** выбранные фильтры. Внутри фильтра по статусу значения объединяются по «или».
4. Порядок (новые первыми) и постраничная выдача не меняются.
5. Выбранные фильтры сохраняются в адресной строке страницы, поэтому не теряются при обновлении и ими можно поделиться ссылкой.

## Сценарии

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | Оператор выбирает один или несколько статусов | в списке только заявки с этими статусами |
| 2 | Оператор задаёт период создания | в списке заявки, созданные в период (границы включительно) |
| 3 | Оператор выбирает исполнителя | в списке заявки этого исполнителя |
| 4 | Оператор комбинирует фильтры | заявки, подходящие под все выбранные фильтры |
| 5 | Заявок по фильтрам нет | сообщение «По выбранным фильтрам заявок нет» |
| 6 | Оператор нажимает «Сбросить» | все фильтры очищены, виден полный список |
| 7 | Период задан неверно (начало позже конца) | запрос не уходит, пользователь видит подсказку; если запрос всё же пришёл, сервер отвечает ошибкой |

## Требования к качеству

- Список с фильтрами отвечает за время, не большее обычного списка (БТ: критерий успеха).
- Целевое значение для согласования: ответ за 1 секунду на 95-м процентиле при миллионе заявок.

## Что вне фичи

- Поиск по тексту названия.
- Сохранение наборов фильтров как пресетов.
- Изменение правил доступа к заявкам.
