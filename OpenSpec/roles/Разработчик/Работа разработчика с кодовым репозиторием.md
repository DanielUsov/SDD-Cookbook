# Работа разработчика с кодовым репозиторием

Разработчик (backend или frontend) реализует свою часть по ФТ из Store. Он отвечает за **содержимое чёрных ящиков**: как реализовать, какие решения принять.

## Что делает разработчик

1. Подключает Store как git submodule (`openspec/store/`) и пинит его на тег: тег фичи `PROJ-1234/vN` во время работы, тег релиза `x.y.z` после архивации ([[OpenSpec/store/Подключение Store к кодовым репозиториям]]).
2. Создаёт локальные changes по схеме superpowers-bridge. Фичу может декомпозировать на несколько changes без отдельных задач в трекере.
3. Заполняет метаданные `proposal.md`: `jira-id` (всегда), `store-feature` и `store-version` (если есть фича в Store).
4. Реализует вместе с агентом: brainstorm, design, specs, tasks, plan, реализация, verify.
5. Архивирует change в локальный master spec **до мержа PR, в той же ветке**.
6. Создаёт PR. Сборка проверяет соответствие кода API-контракту (codegen).
7. Сообщает аналитику об ошибках в ФТ через баг в трекере.

## Правила работы

| Правило | Суть |
|---|---|
| Пин на тег | submodule пинится только на тег (не на коммит и не на ветку) |
| Ссылка на фичу | по ID фичи и версии, не по пути к папке |
| Ветки | gitflow: `feature/PROJ-1234`, `fix/PROJ-1234` |
| Папки changes | читаемый суффикс без ID задачи |
| Одна задача, несколько changes | одна ветка, один PR |
| Отдельные задачи в трекере | отдельные ветки и свои `jira-id` |

## Чтение Store агентом

По умолчанию агент читает только файлы своей части по матрице чтения, которая лежит в инструкциях Store (`docs/`). Это поведение по умолчанию: разработчик вправе прямым промптом расширить чтение (например, на БТ). Запретов нет.

## Проверки

| Что | Где |
|---|---|
| формальные признаки change | pre-push хук |
| результаты проверок | отчёт `verify` в PR |
| соответствие API-контракту | сборка (codegen) |

Остальное (модель данных, поведение, интерфейс, интеграции) разработчик проверяет сам, затем ревью. Подробнее: [[OpenSpec/gates/Контроль соответствия]].
