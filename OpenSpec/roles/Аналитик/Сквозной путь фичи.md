# Первый этап. Входной интерфейс
Аналитик не пишет тексты руками. В корне запускается команда с передачей минимального файла `task.json`
```json
{
  "jiraKey": "CRM-1402",
  "pixsoFrameUrl": "https://pixso.net/app/editor/xxx?node-id=12:34",
  "targetComponent": "src/features/payment/ui/PaymentForm.tsx",
  "swaggerTag": "Payments",
  "businessNote": "Кнопка 'Оплатить' должна блокироваться на 30 сек при 429 ошибке"
}
```
Все остальные данные система извлекает сама из локально склонированных репозиториев (Backend, Frontend, UI Kit) через механизм единого рабочего пространства (`openspec workset`)
# Второй этап. Сбора контекста 
Чтобы агент не захлебнулся в коде и схем (context drift), каждый источник сжимается атомарными утилитами, как самописными, так и готовыми. Запросы к источникам идут либо через REST к ресурсам, либо через MCP, но оборачиваются в обертку в виде субагента, чтобы избежать попадания лишнего контекста к главному агенту. Промежуточный результат сохраняется локально во временные файлы для удобной работы агента и детерминированных CLI-инструментов.
> [!NOTE] Возможность сравнения
> Существует теоретическая возможность сравнения на лету, через формирование XML-состояний As-Is и To-Be. Это реализуется через repomix и xml pixso. Также есть возможность визуального сравнения через мультимодальные модели, но на frontend-проекте должны быть развернуты инструменты для UI-тестирования, например, Playwright. В таком случае есть возможность прямого сравнения, но существует высокая зависимость от качества модуля визуальной обработки в LLM.

Для визуальной части ФТ (поведение UI) используется подход черновика, то есть формируется минимальный черновик, который агент может осознать, ссылки на фреймы из pixso, общее поведение, основываясь на текущем состоянии и БТ. Но **изменение поведения UI требует ручной проверки** и чаще всего доработки.
# Третий этап. Агентный синтез через жесткий шаблон ФТ
Агенту передается жесткий системный навык (Skill / Prompt), принуждающий заполнять только фиксированную структуру через OpenSpec custom scheme. Таким образом, большая часть ФТ формируется агентом.

| **Блок ФТ**                | **Степень автоматизации** | **Что делает система**                                                                                                      | **Ручное действие аналитика**                         |
| -------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| **Контракты API**          | **100%**                  | Берет URL, типы полей, коды ошибок напрямую из Swagger                                                                      | 0 минут                                               |
| **Компоненты UI Kit**      | **90%**                   | Подбирает компоненты и валидные пропсы из Storybook-манифеста                                                               | 1 минута: проверить названия компонентов              |
| **Валидация полей**        | **85%**                   | Считывает regex, длины полей и `NOT NULL` из БД и ФТ Backend                                                                | 1–2 минуты: подтвердить бизнес-маски                  |
| **FSM и BDD сценарии**     | **90%**                   | Генерирует цепочки состояний (Loading, Error, 429, таймеры)                                                                 | 2 минуты: беглая вычитка логики                       |
| **Краевые кейсы**          | **40%**                   | Подсвечивает логические расхождения в секцию `[TBD]`                                                                        | **5–7 минут**: принять бизнес-решение                 |
| **Изминение поведения UI** | **20%**                   | Соберет черновик на основе анализа БТ, UI-кита и Swagger. Будет предполагать поведение при вероятности корректности от 90%. | Валидация и добавление визуального описания поведения |
# Итог
Система, при понятной реализации, будет лишь комплексно помогать и облегчать работу аналитика, но не заменять его полностью. Ресурсы аналитика направлены в основном на описания UI-поведения, из-за недостаточного «понимания» LLM визуального контента.
