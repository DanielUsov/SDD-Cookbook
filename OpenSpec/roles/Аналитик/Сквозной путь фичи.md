# Первый этап. Входной интерфейс
Аналитик не пишет тексты руками. Работа идёт через агента в формате brainstorm, а стартует с минимального входа, например файла `task.json`
```json
{
  "jiraKey": "PROJ-1402",
  "pixsoFrameUrl": "https://pixso.net/app/editor/xxx?node-id=12:34",
  "module": "payments",
  "businessNote": "Кнопка 'Оплатить' должна блокироваться на 30 сек при 429 ошибке"
}
```
Все остальные данные агент получает из Store: master spec нужного модуля, архив прошлых фич и БТ. Код и репозитории сервисов агенту аналитика недоступны (принцип чёрного ящика).
# Второй этап. Сбора контекста 
Чтобы агент не захлебнулся в объёме материалов (context drift), каждый источник сжимается атомарными утилитами, как самописными, так и готовыми. Запросы к источникам идут либо через REST к ресурсам, либо через MCP, но оборачиваются в обёртку в виде субагента, чтобы избежать попадания лишнего контекста к главному агенту. Промежуточный результат сохраняется локально во временные файлы для удобной работы агента и детерминированных CLI-инструментов.

Источники контекста:
- master spec Store по затронутым модулям (`specs/<модуль>/`): текущие контракты, модель данных, поведение;
- архив прошлых связанных фич (`changes/archive/`);
- БТ (`business-requirements/`);
- макеты в инструменте дизайна (для UI-поведения).

Для визуальной части ФТ (поведение UI) используется подход черновика, то есть формируется минимальный черновик, который агент может осознать: ссылки на фреймы из pixso, общее поведение, основываясь на текущем состоянии (`FFRD.md` модуля) и БТ. Но **изменение поведения UI требует ручной проверки** и чаще всего доработки.
# Третий этап. Агентный синтез через жесткий шаблон ФТ
Агенту передается жесткий системный навык (Skill / Prompt), принуждающий заполнять только фиксированную структуру через OpenSpec custom scheme (схема Store). Результат: `FRD.md`, `BFRD.md`, `FFRD.md` и `contracts/` фичи. Таким образом, большая часть ФТ формируется агентом.

| **Блок ФТ**                | **Степень автоматизации** | **Что делает система**                                                                                                      | **Ручное действие аналитика**                         |
| -------------------------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| **Контракты API**          | **100%**                  | Берет пути, типы полей, коды ошибок из текущих контрактов Store и формирует фрагмент `api.yaml`                             | 0 минут                                               |
| **Компоненты UI Kit**      | **90%**                   | Подбирает компоненты и валидные пропсы из Storybook-манифеста                                                               | 1 минута: проверить названия компонентов              |
| **Валидация полей**        | **85%**                   | Считывает длины полей и обязательность из модели данных и `BFRD.md` Store                                                   | 1–2 минуты: подтвердить бизнес-маски                  |
| **FSM и BDD сценарии**     | **90%**                   | Генерирует цепочки состояний (Loading, Error, 429, таймеры)                                                                 | 2 минуты: беглая вычитка логики                       |
| **Краевые кейсы**          | **40%**                   | Подсвечивает логические расхождения в секцию `[TBD]`                                                                        | **5–7 минут**: принять бизнес-решение                 |
| **Изминение поведения UI** | **20%**                   | Соберет черновик на основе анализа БТ, UI-кита и контрактов Store. Будет предполагать поведение при вероятности корректности от 90%. | Валидация и добавление визуального описания поведения |
# Итог
Система, при понятной реализации, будет лишь комплексно помогать и облегчать работу аналитика, но не заменять его полностью. Ресурсы аналитика направлены в основном на описания UI-поведения, из-за недостаточного «понимания» LLM визуального контента.

Общее описание работы аналитика: [[Работа аналитика со Store]].
